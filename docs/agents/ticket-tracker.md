# Local ticket tracker

Tickets and product requirement documents for this repository are stored as Markdown files under `docs/tickets/`.

## Rules

- Store one ticket per Markdown file under `docs/tickets/`.
- Use a stable four-digit sequential number and a short slug, for example `0001-fix-mobile-overflow.md`.
- Before assigning a number, inspect existing files and choose the next unused number.
- Treat the ticket file as the complete source of truth for its title, category, state, description, acceptance criteria, blockers, and history.
- Use exactly one category and one state from `docs/agents/triage-labels.md`. There are no project labels; `Labels` is always `None`.
- A ticket that changes agent behaviour (prompts, gate rules, dialog flows) names the ADR it will add and, once an eval
  harness exists, the eval case ids in its acceptance criteria — prompt wording is covered by evals, not unit tests (see `AGENTS.md`).
- Express dependencies in `Blocked by` using ticket numbers and titles. Use `None` when the ticket can start immediately.
- Keep history auditable. Append material state, scope, and decision changes to `History`; do not erase prior entries to make the ticket look current.
- When a ticket is completed, record the verification performed and update its state to `done`.
- Never update ticket state only in chat. Make the corresponding file change in the same pass.
- A ticket is **closed** when its state is `done` or `wontfix`, and **open** in every other state.
  There is no separate open/closed field — the state is the whole story. `list` filters on this,
  and "close the ticket" in a skill means moving it to `done` (work finished) or `wontfix`
  (deliberately not actioned), never deleting or archiving the file.

## Ticket template

```markdown
# 0001 — Ticket title

**Category:** bug | enhancement
**Labels:** None
**State:** needs-triage | needs-info | ready-for-agent | ready-for-human | wontfix | in-progress | blocked | done
**Blocked by:** None

## What to build

Describe the end-to-end behavior from the user's perspective.

## Acceptance criteria

- [ ] Observable criterion

## Triage notes

Only while the ticket is in `needs-info`. Rewritten in place each round, never appended to.

> *This was generated by AI during triage.*

**What we've established so far:**

- point

**What we still need from you:**

- question

## Notes

Relevant context, constraints, and decisions. Briefs written by triage go here too, under a
`### Agent brief` or `### Human brief` heading, each opening with the AI disclaimer.

## History

- YYYY-MM-DD — Created in `needs-triage`.
```

## Working with tickets

- Create: add the next numbered file from the template and record its creation in `History`.
- Read: inspect the full ticket, including its history and all blockers.
- List: scan `docs/tickets/*.md` and group by state when useful.
- Triage: verify the request against the codebase, then update category, labels, state, notes, and history together.
- Start: ensure all blockers are `done`, change state to `in-progress`, and append a history entry.
- Block: change state to `blocked`, explain the concrete blocker in `Notes`, and append a history entry.
- Complete: check acceptance criteria, record verification, change state to `done`, and append a history entry.
- Reopen: change to the appropriate active state and append why the previous completion no longer holds.

## CLI

`scripts/tickets.mjs` reads and writes these files so agents do not have to hand-edit frontmatter:

```bash
node scripts/tickets.mjs list                    # open tickets as JSON (id, title, state, blockedBy)
node scripts/tickets.mjs list --state ready-for-agent
node scripts/tickets.mjs view 0006               # one ticket, verbatim
node scripts/tickets.mjs set-state 0006 in-progress --note "Picked up in a Claude Code thread."
```

`list` treats `done` and `wontfix` as closed and drops already-`done` blockers from each ticket's
`blockedBy`, so the list shows live dependency edges only. `set-state` rewrites the `State` field and
appends the transition to `History` in one step. Agents call exactly these three commands.

## Where triage output goes

The `triage` skill is written for GitHub Issues — it speaks of applying labels, posting comments,
and closing issues. Here the tracker is files, so each of those maps onto a part of the ticket:

| Skill's action | Where it lands |
| --- | --- |
| Apply a category role (`bug`, `enhancement`) | `**Category:**` |
| Apply a state role (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`) | `**State:**`, via `set-state` so `History` gets the entry |
| Post an agent brief (`ready-for-agent`) | `## Notes`, under a `### Agent brief` heading |
| Post a human brief (`ready-for-human`) | `## Notes`, under a `### Human brief` heading, including why it cannot be delegated |
| Post triage notes (`needs-info`) | `## Triage notes`, using the skill's template |
| Close the issue | `set-state <id> done` or `set-state <id> wontfix` — the file stays |
| Record a rejected enhancement | `.out-of-scope/<concept>.md`, one file per concept, linked from `## Notes` |

Two rules carry over unchanged from the skill:

- **The AI disclaimer is required.** Any section triage writes — a brief, triage notes — opens with
  `> *This was generated by AI during triage.*` on its own line. It marks which prose in the ticket
  a human wrote and which an agent did.
- **Nothing is overwritten silently.** Triage notes are rewritten in place each round, but whatever
  they resolve moves into "What we've established so far" first, and every state change appends to
  `History`. The ticket has to stay readable as a record of how the decision was reached.

## Skill integration

When a skill says to publish to the issue tracker, create or update a file under `docs/tickets/`.

When a skill says to fetch the relevant issue or ticket, read the matching local file. A bare reference such as `#12` or `ticket 12` resolves to the file whose number is `0012`.

The `to-tickets` skill writes one file per approved tracer-bullet ticket directly under `docs/tickets/`, in dependency order. Do not use `.scratch/<feature>/issues/`.
